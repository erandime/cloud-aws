## 1. Re-engineered AWS Architecture for WileyPLUS

To overcome the limitations of lift-and-shift migration and align the WileyPLUS platform with its long-term modernization goals, the second phase of cloud migration adopts a re-engineering strategy. This phase restructures the platform using AWS-native services to move beyond simple re-hosting (Amazon Web Services, 2025t), resulting in a modular, scalable, and cloud-optimised architecture. The re-engineered design leverages modern AWS services and design patterns such as microservices, event-driven workflows, serverless computing, and polyglot persistence.

The re-engineered architecture is illustrated in Figure 2, and the corresponding AWS components and their functions are detailed in Table 3.

![Figure 2. Re-engineered AWS Architecture for WileyPLUS](images/figure-2-re-engineered.png)

**Table 3. Re-engineered AWS Services and Their Functions**

| On-Premises / Lift-and-Shift Component | Re-engineered AWS Replacement | Function |
| :--- | :--- | :--- |
| Akamai CDN | Amazon CloudFront, Amazon Route 53 | CloudFront delivers content through AWS edge locations, reducing latency and securing delivery via AWS WAF (Amazon Web Services, 2025g). Route 53 manages DNS routing, directing users to the optimal CloudFront edge based on latency and health (Amazon Web Services, 2025g). |
| Firewalls | AWS Web Application Firewall (WAF) | WAF, integrated with CloudFront, provides Layer 7 protection against attacks like injection and cross-site scripting (XSS) at the edge (Amazon Web Services, 2025m). Security Groups, NACLs, and Private-subnet segmentation from the lift-and-shift phase are retained for defence-in-depth. |
| Application Load Balancer (ALB) | Amazon Application Programming Interface (API) Gateway | API Gateway becomes the single-entry point for all user requests. It handles routing, throttling, authentication token validation, and secure integration with backend microservices at scale (Amazon Web Services, 2025a). |
| EC2-hosted Application Server Instances (JBoss 4.2.3) in Auto Scaling Group | Amazon Elastic Container Service (ECS) – Fargate Launch Type (Microservices) | The monolithic JBoss application is re-architected into multiple microservices (e.g., RosterSvc, CourseSvc, QuizSvc, GradeSvc) deployed as ECS tasks using the Fargate launch type. These tasks run across private subnets in multiple AZs within an ECS cluster, enabling on-demand, serverless resource allocation (Amazon Web Services, 2025e). |
| EC2-hosted Enterprise Server (ENT) - Tomcat | Amazon Cognito | Cognito provides managed authentication and federated Single Sign-On (SSO) capabilities. It integrates with external LMS identity providers, enabling seamless access for instructors and students using their institutional credentials. It issues and validates tokens, manages user identities, and integrates with API Gateway to authenticate requests before routing to backend services (Amazon Web Services, 2025b). |
| EC2-hosted Tibco instances | Amazon EventBridge, Amazon Simple Queue Service (SQS), Microservices | EventBridge serves as the central event bus for asynchronous, loosely coupled communication between microservices. SQS provides reliable message delivery (Amazon Web Services, 2025k). For example, when a student submits a quiz, the Quiz microservice publishes a “QuizCompleted” event to EventBridge; the Grade microservice subscribes to this event, computes the grade, and stores the result in Aurora. This is one of many similar workflows but is used as a representative example to avoid cluttering the architecture diagram. Traffic to these services is confined within the AWS backbone via VPC Endpoints (Amazon Web Services, 2025i). |
| EC2-hosted content servers | Amazon Simple Storage Service (S3) | S3 provides fully serverless object storage for static content. Integrated with CloudFront, it enables secure, globally distributed static content delivery (Amazon Web Services, 2025h). |
| Amazon RDS for Oracle and MySQL | Aurora Serverless v2, Amazon DynamoDB | Amazon Aurora Serverless v2 provides relational data storage with automatic capacity scaling across multiple Availability Zones in private subnets (Amazon Web Services, 2025o).<br><br>Amazon DynamoDB, a regional NoSQL database, manages session-level data such as quiz attempts and active user sessions with millisecond latency (Amazon Web Services, 2025c).<br><br>VPC Endpoints ensure all DynamoDB access remains within the AWS network for enhanced security and low latency (Amazon Web Services, 2025i). |

### 2.1. Challenges Addressed by Re-engineering and Associated Benefits

Table 4 describes how each challenge identified in the on-premises and lift-and-shift architecture is addressed through re-engineering and outlines the associated benefits.

**Table 4. On-Premises Challenge Themes Addressed through Re-engineering and Its Benefits**

| No | Challenge Theme | How Re-engineering Addresses This and Associated Benefits |
| :--- | :--- | :--- |
| 1 | Global Content Delivery Latency | Akamai is replaced by Amazon CloudFront integrated with Route 53, removing third-party dependencies. All static assets are migrated to Amazon S3, eliminating EC2-based content servers and reducing cache-miss latency. S3 provides durability, availability, and cost-efficiency for data storage (Amazon Web Services, 2025h). For dynamic content, requests are handled by microservices running on ECS with Fargate, which replace JBoss monolith, and by Aurora Serverless v2 + DynamoDB, which replace Oracle + MySQL databases. These services scale automatically on demand and improve transaction speeds (Amazon Web Services, 2025e, 2025o, 2025c). By consolidating static and dynamic delivery within an AWS-native, auto-scaled, and decoupled architecture, the re-engineered design improves global content delivery performance and user experience. |
| 2 | Network and Security Architecture Constraints | AWS WAF integrates with CloudFront to provide perimeter protection and Layer 7 inspection, mitigating application-layer attacks such as SQL injection and XSS at the edge (Amazon Web Services, 2025m). VPC Endpoints connect regional AWS services such as DynamoDB and EventBridge, ensuring that traffic remains within the AWS backbone and eliminating public-internet exposure (Amazon Web Services, 2025i). |
| 3 | Application Layer Limitations | The legacy JBoss monolith is fully decommissioned and re-architected into independent microservices. Amazon ECS (Fargate launch type) enables automatic, demand-based scaling across multiple Availability Zones, enhancing fault tolerance. Each ECS service scales independently, avoiding the resource inefficiency of scaling the entire application stack for demand spikes in specific functions (e.g., roster updates during LMS synchronisation) (Amazon Web Services, 2025e). The modular design isolates failures to individual services, preventing cascading outages. This architecture also supports parallel development and deployment, allowing new features or patches to be introduced without redeploying the full codebase, thereby shortening release cycles and accelerating modernisation.<br><br>Amazon API Gateway acts as a unified entry point, authenticating users via Cognito and routing authorised requests to ECS microservices for execution (Amazon Web Services, 2025a). |
| 4 | Authentication and SSO Bottlenecks | The Enterprise Server (ENT) is replaced by Amazon Cognito, eliminating custom SSO logic and manual scaling. As a fully managed identity service, Cognito automatically scales with user demand, provides built-in support for federated identities, and ensures high availability across multiple AWS Regions (Amazon Web Services, 2025b). By replacing ENT with Cognito, WileyPLUS removes a single point of failure and reduces operational overhead. |
| 5 | LMS Integration Complexity | Tibco is replaced with a combination of containerised microservices running on AWS Fargate, coordinated through Amazon EventBridge and Amazon SQS.<br><br>This architecture enables on-demand scaling, and asynchronous, event-driven, decoupled communication between services, improving performance and responsiveness (Amazon Web Services, 2025k, 2025e). The former integration fragmentation is resolved through a unified, standardised interface for all LMS platforms, reducing operational risk. By removing the external legacy Tibco dependency, this design reduces latency and simplifies maintenance. |
| 6 | Data Layer Limitations | The data tier is modernised through a polyglot persistence model combining Aurora Serverless v2 and DynamoDB (Amazon Web Services, 2025n).<br><br>Aurora Serverless v2 removes manual provisioning and improves scalability for relational workloads. DynamoDB offloads high-velocity session data from relational tier, reducing query delays (Amazon Web Services, 2025r, 2025c). The resulting hybrid model eliminates the vertical-scaling limits of legacy RDS, enhances transaction throughput during peak usage (e.g., exams), and improves user experience.<br><br>It also reduces administrative and licensing overhead by replacing Oracle with managed, auto-scaled, pay-per-use AWS services. |

### 2.2. Limitations of Re-engineered Architecture

* **Migration Complexity:** Decomposing the legacy JBoss monolith into microservices requires extensive code refactoring and dependency untangling (Amazon Web Services, 2025n). Maintaining service continuity during this transition demands careful orchestration and testing across multiple AWS environments.
* **Operational Overhead:** Although server management is reduced through managed services and serverless architecture (e.g., ECS with Fargate, Aurora, Cognito), operational overhead increases due to the distributed nature of microservices. Each microservice requires independent deployment, monitoring, and updates. These are supported through continuous integration and continuous delivery (CI/CD) automation for consistent rollouts and end-to-end observability across ECS, SQS, and EventBridge to monitor inter-service health and communication (Amazon Web Services, 2025u).
* **Learning Curve for Development and Operations:** Teams must transition from JBoss, Oracle, and Tibco to AWS-native services like ECS Fargate, Aurora Serverless, and EventBridge, gaining new competencies in containerisation, serverless computing, and event-driven design. They must also adapt to cloud-native security models and shared responsibility principles (Amazon Web Services, 2025q). Misconfigurations or insufficient AWS security expertise could introduce vulnerabilities.
* **Data Migration and Compliance:** Migrating large-scale sensitive data to Aurora Serverless, DynamoDB, Cognito, and S3 requires robust encryption, downtime planning, and governance to meet institutional and regional data-protection obligations.

## 2. Summary

The final cloud architecture integrates modern AWS services and cloud design patterns, including microservices, serverless computing, event-driven workflows, polyglot persistence, and edge security. These patterns collectively transform WileyPLUS from a monolithic, infrastructure-bound system into a modular, serverless, cloud-native ecosystem. Through this re-engineering, the system achieves greater scalability, resilience, and operational agility compared to both the on-premises and lift-and-shift models. 

The resulting design enhances user experience, performance, and responsiveness while improving adaptability to evolving security threats. It significantly reduces operational overhead, maintenance effort, and resource inefficiency through automation and managed services. Beyond technical gains, this architecture supports Wiley’s strategic objectives of digital modernization and high service availability. A structured project and change management plan is recommended to ensure a smooth transition, mitigate implementation risks, and continuously optimise the new cloud environment.
